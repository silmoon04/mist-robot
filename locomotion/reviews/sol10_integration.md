# Sol10 integration review

Reviewed 12 October 2026. Scope: commands, package imports, portable geometry dependencies, training provenance and handoff documentation. No full training or physical motor operations were run. Core source files were left for the reviser. `locomotion/README.md` now documents the supported direct-script commands and current evidence limits.

## Actionable findings

1. **P1: training freeze fingerprint misses dynamics inputs.** `train.py:31` fingerprints seven files but omits `sensor_sim.py`, its imported `hardware/sensors.py`, the source R7 URDF/manifest and mesh-derived hub/fixture inputs consumed by `model.py`. Editing those during training can change reset dynamics/observations without triggering `check_sources`. Model-report source hashes are not included in `source_hashes`. Include all behavior/model dependencies, record their paths/hashes in each run, and reject changes before checkpoint selection and final evaluation. Verify by changing a copied sensor or source file after capturing the fingerprint and asserting that the freeze check fails. This matters before the final training freeze, not only for published provenance.

2. **P2: default package training import is broken.** `train.py:221` defaults `--env-module` to `mist_env`, and `make_env` imports that literal top-level name. From the repository root, `python -m locomotion.train` parses help but fails once it creates an environment. Reproduced with package import followed by `train.make_env('mist_env', {}, 42)`: `ModuleNotFoundError: No module named 'mist_env'`. Resolve the default according to package context or normalize the module name; retain direct `train.py` use and subprocess workers. Verify actual environment construction in both invocation forms. README documents the existing explicit `--env-module locomotion.mist_env` workaround.

3. **P2: smoke output and remote policy selector disagree.** `scripts/train_smoke.sh` defaults to timestamped `runs/smoke-$run_stamp`, while `sim_remote.py:38` only loads `runs/smoke/{ppo,sac}/final.zip`. Following the default smoke script cannot populate the selector's expected paths. Accept a checkpoint path in a clearly labeled development interface, or align the default output convention. Avoid silently selecting old checkpoints after model changes. README uses an explicit `locomotion/runs/smoke` output argument as the current workaround. No `.zip` checkpoints were present in `locomotion/runs` during review.

4. **P2: CPU setup is pinned at the direct dependency level, not the complete lock.** `setup_cpu.sh` installs a pinned CPU Torch wheel and `requirements.txt`, while `requirements.lock.txt` includes the actual development transitive versions. A future resolver may select different transitives while setup still reports success. If reproducibility is a release requirement, provide a tested complete-lock installation command using the CPU wheel index correctly, and record installed versions. README describes the present behavior accurately. A fresh network installation was not performed in this review.

## Sensitivity follow-up after Sol09 landed

The executor and `validation_cases.json` now exist. Six pure sensitivity tests passed in 0.02 seconds. Independent code review covered scenario bounds, the 130-case plan, contact evidence, CAD-origin velocity correction, metrics and CLI acceptance. Only one tiny physics probe was attempted: `run_case` on `held-out-heavy-stop` with `steps=2`. The physical step path ran, but result generation failed with the blocker below. No full matrix or policy training was run.

5. **P1: sensitivity hashing crashes on source-description prose.** `sensitivity.py:21` tries every string under `config.sources` as a filesystem path. `assembly_scope` is a long prose string; `Path.is_file()` raises `OSError: [Errno 36] File name too long`. Both the plan-only CLI and execution output depend on this hash function. The two-step case reached `run_case`'s return but failed hashing, leaving no result receipt. Hash an explicit set of file-source fields (and required transitive inputs), leaving prose metadata as data. Add a test that invokes the real `source_hashes()` against the shipped config, and a plan-only CLI check. The six pure tests do not exercise this path.

6. **P2: screening provenance is sampled rather than frozen.** The sensitivity executor hashes sources for the outer result and after each case, without comparing them or detecting edits during a case. It also omits imported `hardware/sensors.py` and referenced R7 fixture/visual mesh files. Running a matrix while sources change can mix controllers/dynamics in one output. Capture all behavior/model input hashes before execution, compare before and after each case, and fail explicitly on changes. Freeze checking should happen before launching the full reviewed matrix.

7. **P2: a short probe can be labeled as a complete acceptance pass.** CLI `--steps` accepts one step, and `score_episode` only requires positive duration. A one/two-step stop probe can satisfy every acceptance check although it exercises no sustained stability or full gait cycle. Preserve bounded smoke support, but label it as a probe and require a documented minimum duration for strict acceptance. Record requested/completed duration and an acceptance-complete flag; early truncation should not count as a complete test. Current 500-step defaults are ten seconds, but that is not enforced by the scorer.

The scenario API applies isolated overrides without editing `config.json`: finite bounded mass/strength/voltage/delay/friction scalars, bounded COM/phone offsets, and a reset-options override. Mass scales both mass and principal inertia; COM/phone changes modify the per-environment URDF before load. Motor delay updates the queue in physics steps. CAD body-origin velocity uses COM velocity plus angular cross-offset correction, consistent with rigid-body kinematics. These mechanisms look coherent in review, but the attempted executor probe could not deliver a usable receipt until finding 5 is fixed.

`run_case` deliberately replaces `body_ground_contact` with a stricter any-external-non-toe contact test, including payload links, while `MistEnv` uses a >0.1 N load filter for its own contact info. Document that screening checks a different predicate or use a distinct field name, so the output's contact meaning stays clear. Both paths sample at control boundaries; they do not establish that no brief forbidden contact occurred between physics substeps.
