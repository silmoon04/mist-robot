# Sol07 hardware and sensor review

Reviewed 2026-10-12. No serial connection, flashing or actuation. Only this review file was edited.

The shipped firmware is unconfigured and refuses arming. The bridge also refuses physical gait. Those gates are appropriate: passing replay tests does not establish robot readiness.

## Findings

1. **P2: A recoverable sensor gap permanently disables the estimator.** `hardware/sensors.py:58-60` raises when the interval exceeds 100 ms without resetting `at` or providing a reset method. `BodyIMU.ingest` and the phone accelerometer fallback keep the same estimator, and the CLI catches the error then continues. Replay at MPU timestamps 0, 200, 220 and 240 ms accepts only the first sample; every later sample fails. A phone operating near the simulator's assumed 10 Hz will also fail after modest jitter or one missed pair. Add an explicit recovery state: invalidate the observation, reset only after an acceptable stationary sample or authorized reinitialization, and test resumed packets after dropout, reboot and timestamp wrap. Do not silently resume control on reinitialization.

2. **P2: Simulator dropout behavior does not match hardware rejection.** `sensor_sim.py:131-144` returns the last reading indefinitely and fabricates neutral startup vectors. Staleness appears only in status. `mist_env.py:183` and `:218-221` continue feeding those vectors to the actor and gait compensation; there is no validity feature or control response. Hardware `observation()` rejects stale inputs. Actor and gait correctly share the same delayed reading, but prolonged dropout tests therefore measure a different control system from the prospective hardware runner. Define and test a common missing/stale policy, including startup. If holding is intentional for training, expose validity/age and implement the same bounded hold and subsequent stop in deployment.

3. **P2: The claimed 0.5 rad/s cap includes a renewable allowance.** Firmware `main.cpp:209` grants two additional ticks on every request, and the host grants `2 / TICKS_PER_RAD` per request. At 10 ms intervals, six ticks pass a limit of about 5.26 ticks, permitting about 0.92 rad/s. Faster requests can repeatedly consume the allowance. This is a software rate-bound defect, separate from unknown physical speed. Track a continuous target or a cumulative displacement budget with one rounding allowance, rather than replenishing it per packet. Test several command frequencies and intervals with identical elapsed time.

4. **P2: Disarm can be overtaken by an outstanding arm request in the browser.** Toolbar callbacks call `send()` independently of the interval `sending` flag. HTTP handlers serialize execution through the bridge lock, but do not preserve browser intent order. A user can press Arm and immediately Disarm; if the server processes Disarm first, the later arm request enables torque. STOP latches a fault and blocks this sequence, but Disarm does not. Serialize browser state-changing requests, disable repeated arm while pending, and introduce a session generation/cancellation mechanism so a stop/disarm invalidates earlier outstanding arm intentions. Test deliberately reversed arrival order, including page departure while arm is pending.

## Correctness and limits

Calibration conversion uses `reference + sign * (tick - center) / ticks_per_rad`; its inverse uses the same sign and measured reference, and ordered IDs, finite angles, raw bounds and the host/firmware hash are checked. Firmware reads actual positions before torque enable and preloads those positions. It checks mode, torque state, servo status, current, voltage, temperature and age. The firmware heartbeat and commissioning-window watchdogs do not depend on the browser worker. Broadcast torque-off remains an unacknowledged bus command, so an independent power stop still needs physical verification.

MPU conversion offsets correctly skip the two temperature bytes. Configured +/-2 g and +/-250 degrees/s correspond to 16384 LSB/g and 131 LSB/(degree/s). Android device-axis gyro units, nanosecond timestamps and accelerometer sign agree with the [Android SensorEvent API](https://developer.android.com/reference/android/hardware/SensorEvent). The body-down gravity sign and sensor-to-body rotation are consistent. The [TDK register-map URL](https://invensense.tdk.com/wp-content/uploads/2015/02/MPU-6000-Register-Map1.pdf) failed to load during this review; the conversion assessment also used the existing cited register configuration, rather than claiming a fresh successful document fetch.

Phone gyro and gravity/accelerometer are checked independently for arrival freshness and pair timestamp skew. Moving pan requires both a fresh angle and rate. `rz(angle) @ mount` and subtracting body +Z pan rate are correct only for a measured body-Z pan axis with the stated positive convention. The interface has no pan sensor timestamp, so fresh arrival does not prove alignment with the IMU measurement. Before moving-pan deployment, add a timestamped pan sample and interpolate to the IMU time, or reject excessive skew. The fixed/locked-pan CLI appropriately refuses moving-pan operation.

The simulator uses estimated gravity directly. It explicitly omits raw acceleration, estimator correction/drift, independently delivered Android components and source-clock behavior. Its phone max age is 200 ms whereas hardware defaults to 100 ms; simulator staleness uses measurement age while hardware uses receipt age. These are material deployment assumptions, not evidence of measured Mi 9 SE behavior. The bias option represents residual error in simulation but a correction subtracted in hardware; name or document that distinction in exported profiles. New interfaces should keep measurement timestamp, arrival timestamp, source, validity and frame/unit metadata together, and share one serial owner rather than opening a second monitor beside the bridge.

## Validation evidence

The prescribed Python 3.11 runtime ran `python -m unittest locomotion.hardware.test_bridge locomotion.hardware.test_sensors -q`: 21 tests passed. `python -m pytest locomotion/tests/test_sensor_sim.py -q`: 22 passed, including shared delayed actor/gait input. The tests do not cover the four findings above. A direct estimator-gap replay reproduced finding 1.

All source SHA-256 entries in `hardware/VALIDATION.json` matched current files. That record reports both real PlatformIO builds passing with pinned FTServo and ArduinoJson revisions; both environment directories contain `firmware.elf` and `firmware.bin`. I read that compiler evidence and artifacts; I did not rebuild or upload. The simulator integration is outside that hardware validation manifest.

Missing physical evidence includes actual servo sign/reference/end measurements, pan-axis/lock and sensor mount, gyro bias, transport delay and rate distribution, watchdog timing under bus failures, raw-current scale, thermal behavior and loaded stance. Those omissions justify retaining the gates; they are not software test failures.
